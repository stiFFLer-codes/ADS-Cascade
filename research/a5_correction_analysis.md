# A5 Correction Analysis — dominant-account aggregation bug in `product_ambiguity.csv`

> Follow-up to Research Audit finding A5 (see `determinism_provenance.md` Step 3). That document
> discovered and quantified the bug without changing code. This document records the actual fix:
> the regression test that proves it, the code change, and the before/after impact on every
> downstream synthetic metric. **No manuscript file was touched.** No architecture-decision
> threshold was touched. No production/confidential data exists in this repository, so nothing
> about the production-side numbers cited in `TECHNICAL_REPORT.md` §2.2/§3.2 could be re-verified
> here — see "Paper claims affected" below for what that does and doesn't mean.

## 1. The bug

### Current (pre-fix) grouping

`module_c_behavioral()` in `scripts/03_5_dataset_intelligence.py`, the C.1 "Product Ambiguity"
block, built one list entry **per raw mapping row**:

```python
prod_accs = defaultdict(list)
for m in mappings:
    prod_accs[m["normalized_product"]].append((m["account_id"], m["count"]))
...
acc_list.sort(key=lambda x: x[1], reverse=True)
dominant_account = acc_list[0][0]      # the single largest ROW, not account
dominant_count = acc_list[0][1]
```

`product_account_mapping.csv` has one row per **(company, normalized_product, account_id)**
triple. A product sold by 5 companies to the same account produces 5 separate rows for that one
account. The code above never merges those rows before comparing — it sorts raw rows by count and
takes the biggest single one. If several companies independently agree on the same account, but
each individually books fewer occurrences than one other company's single most-common (but
ultimately minority) account, the vote-split winner is reported as dominant instead of the true
majority account.

### Intended grouping

Counts must be **summed by `account_id` across all rows for the product first**, then the account
with the largest aggregate total is dominant. This is exactly what the neighboring C.3
"Cross-Company Consistency" block already did correctly (`prod_global_accs[prod][m["account_id"]]
+= m["count"]`, a `Counter`) — C.1 was the only block with the bug; C.3 was the reference pattern
the fix now reuses.

### Affected metrics

Everything computed from `product_ambiguity.csv`'s `determinism_score` / `dominant_account_id`
columns for products where the row-level max and the account-aggregate max disagree:

- Weighted ADS and unweighted ADS (`dataset_ads` in `03_5_dataset_intelligence.py`'s return value,
  reused by `04_architecture_decision.py`'s `compute_dataset_ads()`).
- `det_pct` / `amb_pct` — R3's model-complexity input.
- The `dominant_account_id` and `all_accounts` columns themselves (used in "Most Ambiguous
  Products" report listings).
- `n_accounts` (previously counted raw rows, not distinct accounts — also wrong before the fix).

### Metrics NOT affected (and why)

- `cross_company_consistency.csv` / "Global Cross-Company Determinism" (C.3) — already
  account-aggregated, untouched by this change. Confirmed byte-identical after the fix (see §4).
- `company_consistency.csv` / "Average Company Determinism" (C.2) — scoped to a single company's
  rows. Checked `product_account_mapping.csv` directly: **zero duplicate
  (company, product, account) rows exist** (1,234 rows, 1,234 distinct keys), so C.2's
  within-company `max()` over already-deduplicated accounts was never exposed to this bug. No
  change needed or made there.
- `vat_consistency.csv`, `data_quality_report.csv`, `dataset_statistics.csv` — independent data
  paths, untouched.

### Downstream artifacts

`product_ambiguity.csv` → `decision_matrix.csv`, `ai_readiness.csv`, `feature_selection.csv`,
`dataset_intelligence_report.md`, `reports/architecture_decision.md` (all regenerated by
`03_5_dataset_intelligence.py` → `04_architecture_decision.py` in sequence).

## 3. The fix

```python
# Before
prod_accs = defaultdict(list)
for m in mappings:
    prod_accs[m["normalized_product"]].append((m["account_id"], m["count"]))
...
for prod, acc_list in prod_accs.items():
    total = sum(c for _, c in acc_list)
    if total == 0: continue
    acc_list.sort(key=lambda x: x[1], reverse=True)
    dominant_account = acc_list[0][0]
    dominant_count = acc_list[0][1]

# After
prod_accs = defaultdict(Counter)
for m in mappings:
    prod_accs[m["normalized_product"]][m["account_id"]] += m["count"]
...
for prod, acc_counter in prod_accs.items():
    total = sum(acc_counter.values())
    if total == 0: continue
    acc_list = acc_counter.most_common()
    dominant_account = acc_list[0][0]
    dominant_count = acc_list[0][1]
```

`acc_list` still ends up as a list of `(account_id, count)` tuples in descending-count order, so
every line below this block (`n_accounts = len(acc_list)`, the `all_accounts` join, the
`determinism`/`ambiguity_score` math) is unchanged — only the grouping key changed, from "raw row"
to "account, summed." No other function, schema, or interface was touched. `company_consistency.csv`
generation (C.2) was left exactly as-is per §1's finding that it wasn't affected.

## 6. Does the ADS-divergence narrative remain valid?

`TECHNICAL_REPORT.md` §2.2 makes its divergence claim (unweighted 0.964 vs. weighted 0.847, a
0.117 gap) about **production** data, which is confidential and was never run through this
repository's code in this session — it cannot be re-verified here. Per `EVIDENCE_BASELINE.md`
Note 1, whether the identical bug affects production identically is **plausible but unverified**;
this correction does not resolve that question either way.

For the **synthetic** data this repository can actually run, the divergence narrowed materially:
weighted vs. unweighted ADS gap went from 0.1216 (0.9310 − 0.8094) to 0.0566 (0.9597 − 0.9031) —
roughly half its former size, and small enough that `04_architecture_decision.py`'s own
`> 0.1` "ADS Divergence Warning" no longer fires (the warning block is present in the pre-fix
`reports/architecture_decision.md` and absent in the post-fix regeneration). The *direction* of
the divergence (weighted < unweighted, i.e. high-volume products are somewhat less deterministic)
still holds on synthetic data — but the *magnitude* claim, if cited from the synthetic run, is now
roughly half of what it was.

## 8. Summary

**Nothing about which architecture the system should use changed.** All five R1–R5 decisions are
confirmed identical before and after the fix, on the same input data. What changed is the
*reported magnitude* of two synthetic metrics (weighted ADS, deterministic-share) that were
previously understated by a real aggregation bug, and the *size* (not the *existence*) of the
ADS-divergence phenomenon in the synthetic reproduction. This is flagged for human review, not
explained away: three specific numbers in `TECHNICAL_REPORT.md` §3.2/§3.3 are now factually wrong
relative to the corrected, reproducible pipeline and need to be updated when the manuscript
rewrite phase begins.
